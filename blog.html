Automating government benefit implementation with multi-agent AI

How we built a system that transforms a policy request into a complete, tested pull request

The challenge: 2-3 weeks of manual work

Implementing a government benefit program in PolicyEngine requires:

  • Research: Reading statutes, administrative codes, policy manuals, and state plans across 5-10 government sources
  • Translation: Converting legal language like "185 percent of the federal poverty level" into executable Python code
  • Parameterization: Creating 10-20 YAML files with legal citations so every value traces to its source
  • Testing: Writing 20-50 tests covering eligibility rules, benefit calculations, and edge cases
  • Review: Handling 2-3 rounds of feedback on code patterns, naming conventions, and regulatory accuracy
  • Documentation: Updating PR descriptions with formulas, references, and file structures

Each step demands expertise in both tax-benefit policy and PolicyEngine's codebase. We built a multi-agent workflow to automate this process.

The solution: encode-policy

The encode-policy command orchestrates specialized AI agents to automate the implementation process. The command takes a policy request:

/encode-policy "California CalFresh"
/encode-policy "Texas SNAP"
/encode-policy "Oregon TANF"

The output: a pull request with parameters, variables, tests, and documentation.

Architecture: the orchestrator pattern

The encode-policy command never writes code. It invokes specialized agents and checks quality gates between phases.

┌─────────────────────┐ │ ORCHESTRATOR │ │ (encode-policy) │ └──────────┬──────────┘ │ ┌──────────────────────┼──────────────────────┐ │ │ │ ▼ ▼ ▼ ┌─────────┐ ┌─────────────┐ ┌─────────────┐ │ SETUP │ → │ DEVELOPMENT │ → │ VALIDATION │ └─────────┘ └─────────────┘ └─────────────┘

The orchestrator coordinates workflow while specialists handle domain-specific tasks.

Agents and skills

Each agent has:

  • Tools: Capabilities like bash commands, file operations, and web search
  • Skills: Domain knowledge modules (parameter patterns, testing patterns, code style)
  • Model: Claude Opus for complex reasoning

Skills are reusable knowledge modules. The policyengine-variable-patterns-skill contains rules about avoiding hard-coded values, entity levels, and aggregation patterns. Six agents load this skill, ensuring consistent code across the workflow.

The workflow

Phase 1: issue and PR setup

The issue-manager agent:

  1. Searches GitHub for existing issues to avoid duplicates
  2. Creates a new issue with a status template if none exists
  3. Creates a branch (or-tanf, ky-tanf)
  4. Opens a draft PR to the upstream repository

This establishes coordination points for all subsequent agents.

Phase 2: document collection

The document-collector agent researches official sources:

  • State statutes and administrative codes
  • Policy manuals and handbooks
  • State plans submitted to federal agencies
  • Official benefit calculators and examples

The agent discovers the state's official program name (California calls SNAP "CalFresh"), documents eligibility rules and benefit formulas, and flags rules that PolicyEngine cannot simulate (like lifetime time limits).

The output is sources/working_references.md—a single source of truth that all other agents reference.

Quality gate 1: Documentation must include the official program name, income limits, eligibility criteria, and legal citations before development begins.

Phase 3: development

Development happens in three steps:

Step 3A: parameters

The parameter-architect creates YAML files for configurable values:

# income_limit/rate.yaml
description: Oregon limits gross income to this share of the
  federal poverty level under the TANF program.

values:
  2024-01-01: 1.85  # 185% of FPL

metadata:
  unit: /1
  period: year
  label: Oregon TANF income limit
  reference:
    - title: OAR 461-155-0030(2)(c)
      href: https://oregon.public.law/rules/oar_461-155-0030

Key principle: store rates, not dollar amounts. When the federal poverty level updates, calculations adjust automatically.

Step 3B: parallel implementation

Two agents run simultaneously:

  • test-creator works in the tests/ folder, creating tests from documentation
  • rules-engineer works in the variables/ folder, implementing from documentation

Neither agent sees the other's output. This isolation means mismatches reveal bugs or misunderstandings—like two teams implementing the same spec independently.

Step 3C: edge cases

The edge-case-generator analyzes the implementation and adds boundary tests:

  • Income at exactly the threshold
  • Zero income, maximum income
  • Single-person and maximum-size households
  • Benefit cliff effects

Quality gates 2 and 3: Parameter values must match source documents. Implementation logic must match the documented formulas.

Phase 4: organization check

The implementation-validator loads 7 skills and checks:

CheckWhat it validates
NamingVariable names follow prefix conventions
StructureFiles organized logically
ParametersAll metadata present, descriptions formatted correctly
Code patternsadds vs add() usage, reference format
Cross-referencesEvery parameter used, every test variable exists

Output: a structured report with exact code fixes.

Phase 5: test and fix

The ci-fixer agent:

  1. Implements pattern fixes from the validator
  2. Runs tests locally (GitHub CI takes 30-75 minutes)
  3. Analyzes failures
  4. Fixes directly or delegates to specialists

Delegation targets:

  • Calculation errors → rules-engineer
  • Test expectation errors → test-creator
  • Parameter value errors → parameter-architect

The loop continues until all tests pass.

Phase 6: format and push

The pr-pusher agent:

  • Creates or validates the changelog entry
  • Runs formatters (black, isort)
  • Pushes the branch

Phase 7: review

The program-reviewer agent researches regulations before reading the code, preventing confirmation bias. It compares the implementation against source documents and flags discrepancies.

Phase 8: documentation

The reviewer updates the PR description with:

  • Regulatory authority citations
  • Income eligibility tests with sources
  • Benefit calculation formulas
  • Files added and test coverage

The PR remains a draft—humans make the final merge decision.

Design principles

Source authority: Statutes beat regulations beat websites. Every value traces to its most authoritative source.

Isolation: Test creators and implementers don't see each other's work. Mismatches reveal bugs.

Skills as knowledge: Domain expertise lives in reusable modules that multiple agents share.

Orchestrator pattern: The main command never writes code—only invokes specialists and checks quality gates.

Local testing: Run tests locally (2-3 minutes) instead of waiting for GitHub CI (30-75 minutes).

Explicit limitations: Document non-simulatable rules upfront. PolicyEngine uses single-period calculations, so lifetime limits and work history tracking cannot be enforced.

Reusable components: review-pr and fix-pr

The validation and fixing logic from phases 4-7 also exists as standalone commands.

/review-pr runs 4 validators (regulatory accuracy, reference quality, code patterns, test coverage) and posts prioritized findings to GitHub. /fix-pr reads those findings and delegates to specialist agents—parameter-architect, rules-engineer, ci-fixer—to resolve issues automatically.

Both commands work on any PR, not just those created by encode-policy.

Results

The encode-policy workflow compresses 2-3 weeks of manual work into approximately 90 minutes. Specialized agents handle the mechanical work—research, parameterization, testing, documentation—while humans review the final PR and make the merge decision.

The workflow has produced TANF implementations for over 40 states. It has also been used for childcare subsidies and healthcare programs—each following consistent patterns and quality standards.

Try it yourself

The encode-policy command is part of the policyengine-claude repository. To implement a new benefit program:

# Install the plugin
claude /plugin marketplace add PolicyEngine/policyengine-claude

# Run the workflow
claude /encode-policy "Iowa TANF"

The workflow guides you through each phase, checks quality gates, and fixes issues automatically.

What's next

The encode-policy workflow handles individual programs well. The next frontier is understanding how programs interact.

Cross-program validation is our priority. Benefit programs form a connected system. SNAP benefits count as unearned income for TANF eligibility. Medicaid enrollment affects SSI payment calculations. Some programs are mutually exclusive—households cannot receive both. When Program A's output feeds Program B's input, which then feeds back into Program A, circular dependencies emerge. A cross-program validator would detect these interactions during implementation rather than in production.

Historical implementations present a different challenge. Parameters already support multiple effective dates—changing a threshold from $500 to $600 requires only a new YAML entry. But program reforms involve structural changes. A reform might eliminate a deduction entirely, add a new eligibility category, or restructure the benefit formula. These changes require variable logic updates, not just new parameter values. We are testing approaches to handle structural reforms across time.
