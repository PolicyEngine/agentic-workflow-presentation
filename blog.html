Automating Tax and Benefit Policy Modeling with Multi-Agent AI

How we built a system that transforms a policy request into a complete, tested pull request

The manual process

When we add a new state benefit program to PolicyEngine, someone has to translate dozens of pages of legal language into working code. The process follows a predictable pattern: research official sources, extract eligibility rules and benefit formulas, write YAML parameters with legal citations, implement the calculation logic, create integration tests, validate against source documents, and handle multiple rounds of review. Each step requires domain expertise and careful attention to regulatory details.

It typically takes 2-3 weeks. We built a system that does it in 90 minutes.

The solution: encode-policy

The encode-policy command orchestrates specialized AI agents to automate the entire implementation process. The command takes a policy request:

/encode-policy "California CalFresh"
/encode-policy "Texas SNAP"
/encode-policy "Oregon TANF"

The output: a pull request with parameters, variables, tests, and documentation.

Phase 1 — Issue and PR Setup

issue-manager

The workflow begins by establishing coordination points:

  • Searches GitHub for existing issues to avoid duplicates
  • Creates a new issue with a status template if none exists
  • Creates a branch (or-tanf, ia-tanf)
  • Opens a draft PR to the upstream repository

Every subsequent agent references this issue and PR for coordination.

Phase 2-3 — Document Collection & Development

document-collector parameter-architect test-creator rules-engineer edge-case-generator

Phase 2: Research — The document-collector researches official sources: statutes, policy manuals, state plans, and benefit calculators. Output: sources/working_references.md

Quality gate 1: Documentation must include the official program name, income limits, eligibility criteria, and legal citations.

Phase 3: Build — Three parallel tracks:

  • Parameters: The parameter-architect creates YAML files with legal citations
  • Implementation: test-creator and rules-engineer work simultaneously from the same docs — neither sees the other's output
  • Edge cases: The edge-case-generator adds boundary tests

Quality gates 2 & 3: Parameter values must match source documents. Implementation logic must match documented formulas.

Phase 4-6 — Validation & Fixes

implementation-validator reference-validator ci-fixer pr-pusher

Phase 4: Organization check — The validator loads 7 skills and checks naming conventions, file structure, metadata completeness, code patterns, and cross-references.

Phase 5: Validate and fix — First, the reference-validator checks that all parameters have proper citations. Then the ci-fixer runs tests locally (2-3 min vs 20-30 min on GitHub CI), analyzes failures, and delegates to specialists:

  • Calculation errors → rules-engineer
  • Test expectation errors → test-creator
  • Parameter value errors → parameter-architect

This cycle repeats until all tests pass.

Phase 6: Format and push — The pr-pusher adds changelog, runs formatters (black, isort), and pushes.

Phase 7-8 — Review & Complete

program-reviewer

Phase 7: Review — The program-reviewer researches regulations before reading code (preventing confirmation bias), then compares implementation against source documents. If discrepancies are found, findings are posted to the PR for human review.

Phase 8: Documentation — The reviewer updates the PR description with:

  • Regulatory authority citations
  • Income eligibility tests with sources
  • Benefit calculation formulas
  • Files added and test coverage

The PR remains a draft — humans make the final merge decision.

Agents and skills

Each agent is configured with:

  • Tools: A specific set of capabilities (bash commands, file operations, web search) tailored to its task
  • Skills: Domain knowledge modules (parameter patterns, testing patterns, code style, etc.)
  • Model: Claude Opus for complex reasoning

Skills are reusable knowledge modules. The policyengine-variable-patterns-skill contains rules about avoiding hard-coded values, entity levels, and aggregation patterns. Six agents load this skill, ensuring consistent code across the workflow.

Skills follow Anthropic's Agent Skills open standard, which works across multiple AI tools. See the Claude Code documentation for details.

Design principles

Source authority: Statutes beat regulations beat websites. Every value traces to its most authoritative source.

Isolation: Test creators and implementers don't see each other's work. Mismatches reveal bugs.

Skills as knowledge: Domain expertise lives in reusable modules that multiple agents share.

Orchestrator pattern: The main command never writes code—only invokes specialists and checks quality gates.

Local testing: Run tests locally (2-3 minutes) instead of waiting for GitHub CI (20-30 minutes).

Explicit limitations: Document non-simulatable rules upfront. PolicyEngine uses single-period calculations, so lifetime limits and work history tracking cannot be enforced.

The evolution: from prompt to workflow

The current system didn't emerge fully formed. It evolved through several iterations, each solving problems revealed by the previous approach.

Stage 1: One long prompt

We started with a single prompt asking Claude to implement a TANF program end-to-end. The results were poor—too many aspects for one context to handle well. Research, parameters, variables, tests, documentation—each requires different expertise and attention.

Stage 2: Specialized agents

Breaking the work into specialized agents helped: a research agent, a parameter agent, a test agent, a variable agent. Each prompt taught the agent how to build for the policyengine-us repository. But without a skills feature (this was before October 2025), prompts were long and redundant. The same patterns—naming conventions, file structure, code style—appeared in every agent's instructions, often inconsistently.

Stage 3: The test problem

The most critical issue: tests designed to pass, not to verify. When a test agent sees implementation code and writes tests afterward, the tests validate what was built rather than what the regulation requires. A bug in the formula and a matching bug in the test cancel out—everything passes, nothing is correct.

The solution: run test-creator and rules-engineer in parallel. Both read the same documentation, neither sees the other's output. When tests fail, it reveals actual discrepancies. We added an edge-case-generator that creates boundary tests after implementation—covering zero income, maximum benefits, cliff edges—based on real-world scenarios rather than implementation details.

Stage 4: The forgetting problem

Results improved, but formatting and code style issues persisted. The likely cause: prompts had grown so long that agents "forgot" rules buried in pages of instructions. Important patterns got lost in the noise.

Then Claude Code released the skills feature in October 2025. Skills let us extract domain knowledge into reusable modules that agents load on demand. Instead of one agent prompt containing everything about parameters, variables, testing, aggregation, vectorization, and code style, we created focused skills for each concern. Agents load only what they need. The rules-engineer loads policyengine-variable-patterns-skill and policyengine-code-style-skill. The test-creator loads policyengine-testing-patterns-skill. No redundancy, no forgetting.

We re-engineered every agent and workflow around skills. The improvement was significant.

Stage 5: User feedback

Colleagues using the workflow provided feedback that shaped new features. They wanted to review PRs created outside the workflow. They wanted to fix issues without re-running the entire pipeline. This led to /review-pr and /fix-pr—commands that reuse the same agents (validators, specialists, ci-fixer) but expose them for standalone use. The components became building blocks, not just steps in a sequence.

Reusable components

Every agent and skill in the workflow can run independently outside the encode-policy flow. The /review-pr and /fix-pr commands demonstrate this—they use the same validation and fixing agents to review any PR, not just those created by encode-policy.

/review-pr runs 4 validators (regulatory accuracy, reference quality, code patterns, test coverage) and posts prioritized findings to GitHub. /fix-pr reads those findings and delegates to specialist agents—parameter-architect, rules-engineer, ci-fixer—to resolve issues automatically.

Skills work the same way. The policyengine-testing-patterns-skill can be loaded by any agent or user session to get consistent test formatting rules. Skills are context you can inject into any conversation—not tied to specific commands or workflows.

Results

Specialized agents handle the mechanical work—research, parameterization, testing, documentation—while humans review the final PR and make the merge decision.

The workflow has produced TANF implementations for 42 states, generating over 60,000 lines of code. We have also used it for childcare subsidies and healthcare programs, each following consistent patterns and quality standards.

Try it yourself

The encode-policy command is part of the policyengine-claude repository. To implement a new benefit program:

# Install the plugin
claude /plugin marketplace add PolicyEngine/policyengine-claude

# Run the workflow
claude /encode-policy "Iowa TANF"

The workflow guides you through each phase, checks quality gates, and fixes issues automatically.

What's next

The encode-policy workflow handles individual programs well. The next frontier is understanding how programs interact.

Cross-program validation is our priority. Benefit programs form a connected system—SNAP benefits count as unearned income for TANF, Medicaid enrollment affects SSI calculations, and some programs are mutually exclusive. A cross-program validator would detect these interactions during implementation rather than in production.

Historical implementations present a different challenge. Parameters support multiple effective dates, but program reforms often involve structural changes—eliminating deductions, adding eligibility categories, or restructuring formulas. We are testing approaches to handle these reforms across time.
