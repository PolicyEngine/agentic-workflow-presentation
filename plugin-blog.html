PolicyEngine + Claude Code

How We Turned Claude into a Policy Expert

Without training a model

PolicyEngine models tax and benefit policy for 50+ US state programs and multiple countries. Our ecosystem spans 40+ repositories, thousands of parameters, and a codebase where a single misread regulation can produce wrong numbers for millions of households.

We needed our AI coding agent to understand all of it. So we built policyengine-claude—a Claude Code plugin that packages our entire domain into something Claude can use at runtime.

No fine-tuning. No training data. Just structured knowledge, specialized agents, and a few clever guardrails.

What It Does

The plugin gives Claude three things:

39

Skills

Domain knowledge files covering everything from PolicyEngine variable patterns to US tax law to NumPy vectorization. Each skill is written for three audiences: users learning the platform, analysts running simulations, and contributors writing code.

30

Agents

Specialized workers that handle specific jobs. A rules-engineer implements tax variables. A test-creator writes integration tests. A document-collector researches government regulations. A program-reviewer checks implementations against the law. They work together through orchestrated workflows.

8

Commands

Multi-agent workflows that chain agents together into end-to-end pipelines. /encode-policy takes a government program from legal text to working code, with regulatory checkpoints along the way.

/encode-policy pipeline
Research law → Checkpoint → Design parameters → Checkpoint → Write tests → Implement logic → Checkpoint → Validate

The Key Ideas

Documentation Pointers, Not Stale Examples

Most knowledge bases rot. You write example code, the codebase evolves, and now your examples are wrong.

We solved this by having skills point to live code in repos instead of hardcoding examples. When Claude reads a skill, it gets instructions like “look at the current implementation in policyengine_us/variables/”—always fresh, always branch-aware, zero maintenance.

Legal Code Is the Source of Truth

When implementing a government benefit program, the temptation is to copy what another state does and tweak it. Our agents are instructed differently: read the actual regulation first, understand what the law says, then implement exactly that. Pattern-matching across states is a tool, not a shortcut.

Zero Hard-Coding

Every dollar amount, every threshold, every phase-out rate lives in a parameter file—never as a magic number in code. This is what makes PolicyEngine work: you can simulate policy reforms by changing parameters alone. Our agents enforce this automatically.

Claude Policing Claude

We use Claude Code hooks—prompts that run before or after tool calls—to enforce architectural rules. When Claude writes a file, another Claude prompt checks whether tax logic ended up somewhere it shouldn’t be. If it did, the write gets blocked.

The same mechanism auto-detects which PolicyEngine repo you’re in and routes you to the right specialized agents. Open Claude Code in policyengine-us and it knows to use the rules-engineer, not a generic agent.

What We Learned

Structure beats volume. A well-organized 200-line skill file is worth more than a 2,000-line knowledge dump. Claude works best when knowledge is modular and clearly scoped.

Agents need constraints, not just capabilities. The most impactful additions weren’t new features—they were guardrails. Regulatory checkpoints. Architecture enforcement. The rule that agents must read the law before writing code.

Plugins are prompt engineering at scale. You’re not training a model. You’re building a structured context that makes a general-purpose model behave like a domain expert. That’s powerful and accessible—anyone can do it.

Try It Yourself

If your team has domain knowledge scattered across docs, wikis, and tribal memory, a Claude Code plugin can consolidate it into something an AI agent actually uses. Start with a few skills, add agents for your key workflows, and let hooks enforce your rules.
