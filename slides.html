Phase 0

Implementation Approach Detection

For TANF programs, detect the appropriate implementation strategy:

Simplified (Default)

  • Use federal baseline variables
  • Only create state-specific logic where needed
  • Faster implementation
  • Works for most states

Full

  • Create everything state-specific
  • Complete custom implementation
  • Required for unique state definitions
  • More comprehensive
# Auto-detection from user's request: "simple Oregon TANF" → Simplified "full implementation of Texas TANF" → Full "implement Montana TANF" → Default to Simplified

Step 3B

Parallel Development: Isolation by Design

🧪 test-creator

Works in tests/ folder

  • Creates tests from documentation ONLY
  • Doesn't see implementation
  • Unit tests + integration tests
  • Documents calculations in comments

⚙️ rules-engineer

Works in variables/ folder

  • Implements from documentation ONLY
  • Doesn't see tests
  • ZERO hard-coded values
  • Proper vectorization patterns

Why isolation? When outputs meet, mismatches reveal bugs or misunderstandings — like separate teams implementing the same spec

Step 3B

rules-engineer: Key Patterns

Critical Rules:

# Pure sum → use adds (no formula!) adds = ["earned", "unearned"] # Sum + operations → use add() def formula(spm_unit, period, params): total = add(spm_unit, period, ["earned", "unearned"]) return max_(total - deduction, 0) # NEVER do this: earned + unearned # ❌ Manual add

Simplified TANF:

  • Use federal baselines directly
  • Don't create wrapper variables
  • Only state-specific logic needed

Don't create:
state_tanf_gross_earned_income
Use instead:
tanf_gross_earned_income (federal)

Phase 4

implementation-validator

The quality inspector — loads 7 skills and checks everything:

Check What It Validates
Naming Variable/parameter names follow prefix conventions
Structure Files organized logically, no subfolder for single files
Parameters All metadata present, descriptions formatted correctly
Code Patterns adds vs add(), tuple not list for refs
Cross-refs Every parameter used, every test variable exists
Wrappers No unnecessary wrapper variables

Output: Structured report with exact code fixes for the next agent

Phase 5

ci-fixer: Fix vs Delegate

✅ Fix Directly

  • Entity mismatches
  • Test syntax errors
  • Missing imports
  • Unnecessary wrapper variables
  • Code style issues

🔄 Delegate to Specialist

  • Calculation errors → rules-engineer
  • Test expectations wrong → test-creator
  • Parameter values wrong → parameter-architect
  • Edge case logic → edge-case-generator

Loop continues until all tests pass locally

Design Principles

Source Authority: Statutes → Regulations → Websites (hierarchy of trust)
Isolation: Test writer and implementer don't see each other's work
Skills as Knowledge: Domain expertise in reusable modules
Orchestrator Pattern: Main command never writes code — only invokes agents
Local Testing: Don't wait for CI — iterate fast locally
Explicit Limitations: Document what we can't simulate upfront
